Images in the loop: reading what callers send

Halfway through a booking call, the caller says "I've got a letter from my doctor". Nobody wants them to read it aloud, letter by letter, into a phone. So the agent texts them a link, they photograph the letter, and now your voice agent has a picture to read while the call is still running. Tonight we follow that photo from the caller's camera to the model, choose how to read it, pull the fields into a strict schema, and then do the part a schema cannot: say the important values back to the caller and listen for "no, that's wrong". Images here are input only; nothing gets generated.

Part 1 · covers vision input mechanics

How a photo gets into a call

5 min live

During a Callwell call (constructed), the agent texts the caller a link. The caller takes a photo of their referral letter and sends it. Your server receives the file and stores it. From there, the model needs to see the image, and there are only three ways to hand it over. Which one you choose decides how much you pay every turn for the rest of the call.

LiveThree ways to hand over an image3 min▶

OpenAI's images and vision guide (read 2026-11-08) lists exactly three: "a fully qualified URL to an image file", "a Base64-encoded data URL", or "a file ID (created with the Files API)". Anthropic's vision docs offer the same shapes. For a one-shot question, any of them works. For a phone call, the image has to survive a conversation: the caller confirms a field, asks a question, changes the slot, and every turn is a fresh model call that carries the context.

That is where the choice bites. Anthropic's docs say it directly for agent loops: a base64 image is sent again with every turn, so use the Files API and pass a file_id instead. A public URL is also a reference, but a referral letter does not belong at a public address; keep it in your own storage and hand the model the id.

OpenAI also exposes a detail setting: low ("Coarse image understanding"), high, original for large, dense images where the model supports it, and auto, the default. Do not assume low saves money: the guide warns that "low does not always use fewer tokens than high". For a letter with small print, coarse is the wrong goal anyway.

Self-studyCost and size limits, dated3 min▶

Anthropic's vision docs, read 2026-11-08 (vendor documentation, re-verify before you rely on it):

  • Dimensions: "The maximum dimensions for each image are 8000x8000 px." Send more than 20 images and a stricter per-image limit applies; the safe rule on the page is to keep each side under 3,000 px or send 20 or fewer.
  • File size: 10 MB per image on the Claude API. Formats: JPEG, PNG, GIF, WebP.
  • Cost: counted in 28 x 28 px patches, "referred to as a visual token": ceil(width / 28) x ceil(height / 28). The page's own example, 1000 x 1000 px, comes to 1,296 tokens.

One more capability to watch: OpenAI's realtime conversations guide (read 2026-11-08) says gpt-realtime-2 and gpt-realtime "also support image input". That means a speech-to-speech session could, in principle, see the letter inside the same conversation. Model names change monthly; re-verify before you rely on it, and note that the guide names those two models, not every realtime model.

Real world

The vendor tells you where the money leaks. Anthropic's vision docs (read 2026-11-08) single out agent loops: base64 images are resent on every turn, and the fix they name is the Files API. A ten-turn booking call that carries a letter photo as base64 pays for that photo ten times; with a file id, it sends a reference. The arithmetic is yours to run on your own image sizes, with the patch formula above.

Part 2 · covers the reading choice

OCR or a vision model

5 min live

Once the image is in reach, something has to read it. Optical character recognition (OCR) turns pixels into words. A vision model reads the page the way a person glances at it: layout, headings, which line is the date. No source we read compares the two on referral letters, so treat what follows as a design trade-off from practice, not a measured ranking.

LiveWhen OCR wins2 min▶

OCR gives you text, a bounding box for each word and a confidence number per word. It gives you no meaning: it does not know that "14/03" is the letter's date rather than an appointment. It wins when the document has a fixed layout you can map by position (a form you designed, always the same boxes), when you need a per-word confidence you can threshold, or when you want a cheap first pass that tells you the photo is too blurry before you spend a model call on it.

LiveWhen a vision model wins2 min▶

A vision model reads layout and meaning: it can find "the referring clinician" on a letter it has never seen, from any practice, in any template. That is most of Callwell's problem, because every practice writes letters differently. The cost is that it gives no calibrated per-field confidence unless you ask for one, and a confidence the model writes about itself is a guess, not a measurement.

Both vendors publish where it struggles (read 2026-11-08). OpenAI lists small text, rotated text, non-Latin text, approximate counting and weak precise localisation, and says the model has no access to file names or metadata. Anthropic says Claude "might hallucinate or make mistakes when interpreting low-quality, rotated, or very small images under 200 pixels", that coordinates are approximate, and that "heavy JPEG compression can make text difficult to read". A phone photo of a folded letter on a kitchen table can hit several of those at once.

Self-studyThe hybrid, and the tips that help either way3 min▶

The hybrid runs OCR first and passes both the OCR text and the image to the vision model. The model does the reading for meaning; the OCR confidences tell you which fields rest on shaky pixels, so your code (not the model) decides what to ask back. It costs two calls and some plumbing. Whether it beats either alone on your letters is something only your own sample can tell you.

Whichever you choose, the vendor tips apply. Anthropic: "If the image contains important text, make sure it's legible and not too small", and label pages "Image 1:", "Image 2:" when a caller sends a two-page letter. OpenAI: enlarge small text, or use detail: original where the model supports it. On the call itself, that becomes a sentence the agent can say: "If you can, lay the letter flat near a window and take the photo straight on."

Real world

Both vendors say "not for diagnosis", in writing. OpenAI's vision guide (read 2026-11-08): "The model is not suitable for interpreting specialized medical images like CT scans." Anthropic's vision docs say Claude is not designed to interpret complex diagnostic scans such as CTs or MRIs. A referral letter is not a scan, but the line is the same one Callwell draws: the agent reads where to route the letter, never what it means for the patient.

Part 3 · covers structured extraction and confidence

Extract to a schema, then ask back

5 min live

The booking tool needs fields, not prose. So you ask the model to return JSON that fits a schema, and with strict mode on you get JSON that fits every time. That feels like safety, and it is half of it. A schema checks the shape of the answer. It cannot check that "4/03" was really "14/03" on the paper. On a phone call, the only one who can check that is the caller, so the agent says it back.

LiveWhat the schema guarantees, and what it does not2 min▶

OpenAI's Structured Outputs guide (read 2026-11-08) is precise: with "strict": true, it "ensures the model will always generate responses that adhere to your supplied JSON Schema". Plain JSON mode does not; it gives valid JSON, but "only Structured Outputs ensure schema adherence". Two exceptions are written into the same guide: "a refusal does not necessarily follow the schema you have supplied", and output cut off early (for example by a token limit) may not match either. Your code has to handle both.

Read the guarantee again: adherence to the schema. It says nothing about whether the value was read correctly from the photo. A misread date is still a string. So design the schema to make uncertainty speakable: nullable values, a status of read, unreadable or absent per field, a short evidence quote copied from the letter, and a legibility flag for the whole photo.

LiveAsking back by voice2 min▶

Text agents show a form and let the user correct it. A caller cannot see the form, so the agent reads the critical fields aloud, one at a time, slowly, and waits. Read dates as words ("the fourteenth of March"), never as digits, because "fourteen oh three" invites the very misread you are checking for. Spell a clinician's name only if the caller hesitates.

Pick the critical fields deliberately: the ones that would book the wrong person, place or day. For Callwell that is the clinician and the letter date. If a critical field came back unreadable, the agent asks the caller for it ("I couldn't read the date on the letter, could you tell me what it says?"). If the caller cannot help either, the booking goes to a person.

Self-studyNever interpret clinical content: the agent routes, a clinician reads2 min▶

The reason for referral is extracted in plain words, copied from the letter, for one purpose: picking the right service and site. The agent never paraphrases it into advice, never judges whether it sounds serious, and never answers "is that bad?". If the letter's urgency box is ticked, or the caller asks a medical question, the rule is the same: route to a person. That boundary belongs in the agent's guardrails, which learn-ai-agents, guardrails covers; here it just becomes a line in the routing rule.

The photo itself is health information the moment it arrives. How long you keep it, who can see it and what your contracts say are questions for your privacy rules and your regulator, not for a prompt. Session 6 says the little that can be said generally about data handling on calls.

Real world

The guarantee comes with its own exceptions, from the same page. OpenAI's Structured Outputs guide (read 2026-11-08) promises schema adherence and, a few sections later, tells you a refusal "does not necessarily follow the schema you have supplied". A production extractor checks for the refusal field and for truncated output before it parses anything, and treats both as "send to a person", not as a crash.

Build-along

Read Callwell's invented referral letter

★ 22 min · everyone builds

Below is the letter a Callwell caller (constructed) photographs. It is invented from top to bottom: the practice, the clinician, the patient and the date. One field is smudged on purpose. Write the six pieces in order; if your product reads a different document, an invoice, a delivery note, an insurance card, write yours alongside and keep Callwell as the worked answer. Nothing here is run for you: the example output in step 4 is constructed, and your model's will differ.

List the fields the booking actually needs. Start minimal. Every extra field is one more thing to misread, confirm and store. If the booking tool would not use it, do not extract it.

★ Step 1 · the minimal field listsite which Callwell site the letter is addressed to clinician the referring clinician, for the booking note reason plain words copied from the letter, for routing only letter_date referrals can expire; the booking checks it urgency routine or urgent, as ticked on the letter legibility is the photo good enough to trust at all? Left out on purpose: patient details (the caller is on the line and already identified), the letter body, the signature

Write the JSON schema. Strict, every field required, each value nullable, a status that can say "unreadable", and an evidence string so a person can check the model's work later.

★ Step 2 · strict schema, one field shown in full{ "name": "referral_fields", "strict": true, "schema": { "type": "object", "additionalProperties": false, "required": ["site", "clinician", "reason", "letter_date", "urgency", "legibility"], "properties": { "letter_date": { "type": "object", "additionalProperties": false, "required": ["value", "status", "evidence"], "properties": { "value": { "type": ["string", "null"] }, "status": { "type": "string", "enum": ["read", "unreadable", "absent"] }, "evidence": { "type": "string" } } }, "legibility": { "type": "string", "enum": ["clear", "partly_readable", "unreadable"] } ... site, clinician, reason, urgency: same shape as letter_date } } }

Write the extraction instruction. It tells the model to copy, not to interpret, and makes "unreadable" the safe answer instead of a failure.

★ Step 3 · extraction instructionYou are reading a photo of a referral letter sent by a caller. Fill every field in the schema. - Copy values exactly as written. Do not correct, expand or guess. - If any character of a value is hard to read, set status "unreadable" and value null. Do not fill in a likely value. - If the field is not on the letter, set status "absent". - evidence: quote the words you read, up to 10 words, or "" if there are none. - reason: copy the letter's own words. Do not summarise, rephrase or comment on them. - Do not give any medical opinion. You are routing a booking.

Look at an example output. This one is constructed to show the shape you want, with the smudged date coming back as unreadable rather than a confident guess. Your model's output will differ; run it on your own photos.

★ Step 4 · example output (constructed, your model's will differ){ "site": { "value": "Callwell Riverside", "status": "read", "evidence": "To: Callwell Riverside, physiotherapy" }, "clinician": { "value": "Doctor Lindqvist", "status": "read", "evidence": "From: Doctor Lindqvist" }, "reason": { "value": "knee pain, physiotherapy assessment", "status": "read", "evidence": "Reason: knee pain, physiotherapy assessment" }, "letter_date": { "value": null, "status": "unreadable", "evidence": "Date of letter: [smudged]" }, "urgency": { "value": "routine", "status": "read", "evidence": "routine box ticked" }, "legibility": "partly_readable" }

Write the spoken ask-back. Critical fields only, one at a time, dates in words. The caller should be able to say "no" after each one.

★ Step 5 · ask-back scriptAgent: Thanks, I've got the letter. I'll check two things with you. Agent: It's from Doctor Lindqvist at Harbour Family Practice. Is that right? Caller: Yes. Agent: I couldn't read the date on the letter. Could you tell me the date written at the top? Caller: The fourteenth of March. Agent: The fourteenth of March. Thank you. I'll book you with physiotherapy at Riverside. (If the caller corrects a field: say the corrected value back once, then store it with status "confirmed_by_caller".)

Write the routing rule. The cases where the agent stops reading and a person takes over, with what gets handed over so the caller does not start again.

★ Step 6 · routing ruleRoute to a person (warm handoff, session 6) when ANY of: - a critical field (site, clinician, letter_date) is "unreadable" AND the caller cannot supply it - legibility is "unreadable" after one request for a new photo - urgency is "urgent" or anything other than "routine" - the model refused or the output was cut off - the caller asks what the letter means or any medical question Hand over: the stored file id, the extracted fields with status and evidence, and which fields the caller confirmed by voice.

"Unreadable" is a good answer. The schema made it a legal value, the instruction made it the safe one, and the ask-back turned it into a two-second question. The thing to fear is a confident wrong value that passes every check, which is exactly why the date is read back even when its status says "read".

Homework

Before session 5

30 min
  1. Draw your own photo path. Camera to model, with where the file is stored and whether the model gets a URL, base64 or a file id. Circle every turn that would resend the image.
  2. Make five bad photos. Use an invented document of your own, never a real one: one rotated, one blurry, one folded, one in low light, one heavily compressed. Run your extractor on all five and count how many fields come back confidently wrong rather than "unreadable".
  3. Cut your field list. For each field you extract, write which tool or decision uses it. Delete any field with no answer.
  4. Say your read-back aloud. Read your ask-back script to someone over a phone. Note every place they hesitated or misheard; rewrite those lines.
Check yourself

Three questions

Clear all three and session 4 gets stamped in your passport.

1 · Your extractor uses Structured Outputs with strict mode on. What does that guarantee about the letter date it returns?

OpenAI's guide promises responses that "adhere to your supplied JSON Schema": shape only. A misread "4/03" is still a valid string. Refusals and cut-off output are the guide's own exceptions, and JSON mode does not ensure schema adherence at all.

2 · In a ten-turn booking call, the agent sends the letter photo to the model as a base64 data URL. What happens, and what is the fix the vendor docs name?

Anthropic's vision docs say base64 images are resent every turn and recommend the Files API in agent loops. A public URL is the wrong home for a referral letter anyway.

3 · The letter date comes back with status "unreadable". The caller, asked, cannot find the letter any more. What should the agent do?

An unreadable critical field the caller cannot supply is a routing case, not a guessing game. Handing over the file id and the confirmed fields means nobody asks the caller to start again.
